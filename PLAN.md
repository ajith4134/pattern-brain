## 0. Core architectural principle (owner-confirmed 2026-06-20, Block 30 — governs everything below)
✅ **DECIDED: build domain-independent first; adapt the data to the system second — never the reverse.** Owner: "we are not building this project focused on data like candles or order book but build them independent of that and after implementing them we convert the data related [to] stocks into the inputs they need, not the other way around."

**What this means concretely:** the model bank (§5), the Connector Intelligence, the graph, and the evolution/mutation engines (§4, §6) are defined first by each component's own native, generic interface — e.g. "an HMM consumes a sequence of D-dimensional vectors and emits a state distribution" — with **zero reference to candles, order books, or any stock-specific shape**. Only *after* those components exist does a separate, swappable adapter convert real stock-market data into whatever input shape they already require. The data adapts to the system; the system is never reshaped around what one particular data source happens to offer.

**Why this matters, and what it confirms:** this is the same "protocol first, devices adapt to it" principle already running through Blocks 4-5's internet/compiler analogies and Block 16/18's "electronic components" analogy — just now stated as a governing rule for the *whole project*, not only the belief-format layer. It also explains, more precisely than before, *why* this project is kept structurally separate from the trading bot (Rule 1): Pattern Brain's identity is a general-purpose pattern-finding/sequence-prediction architecture; stock/trading data is the *first domain plugged into it via an adapter*, not what the architecture is built around. A second domain (e.g. a completely different data type) should be pluggable later via a new adapter alone, without touching the model bank or Connector Intelligence at all — that portability is the actual test of whether this principle was followed correctly.

**Concrete consequence — the build order (Implementation Progress Tracker, below) had this backwards and is corrected:** the original order (Block 24) put stock-data-specific work (time/asynchrony handling, a candle translation layer) in steps 1-2, *before* the model bank in step 3. Under this principle, the model bank and Connector Intelligence must be defined first (in their own generic terms), with the stock-data adapter built afterward, specifically to feed them. Reordered below.

**Open tension flagged, not silently resolved (Rule 15):** the evaluator (§4) scores candidates using Sharpe Ratio, Drawdown, and similar metrics — these are inherently *financial* concepts, not domain-agnostic ones. Strictly applying this principle would mean the evaluator's objective function should also be a pluggable, domain-specific adapter (financial metrics for the stocks domain, something else for a future domain) rather than hardcoded into the evaluator's core design. Not yet decided — flagging the inconsistency rather than pretending the principle has been applied everywhere already.

**Enforced going forward by Rule 23** (`RULES.md`) — every future architecture/feature/build-order proposal in this project gets checked against this principle before it goes into the plan, specifically so this doesn't silently drift again the way Block 24's build order did.

## 4. Planned features
✅ **DECIDED — sequencing (2026-06-20):** Features 1, 2 & 3 below, together with their shared evaluator, are the **FINAL implementable features** in this whole plan — built only after everything else in §5 (model bank/taxonomy) and §6 (translation pipeline, Connector Intelligence) is implemented first. Owner's explicit instruction: "make these features... part of this plan to be implemented after the entire plan is implemented as the final implementable features," then "update the plan with all you mentioned along with graph/pathway Evolution Engine."

🧩 **Feature 1 — ML Model Creation + Mutation.** Operates *within* a fixed, known algorithm (an HMM, an LSTM, etc.): create new trained instances; mutate deployed ones via hyperparameter changes, small architecture tweaks, partial retraining, or crossover between two trained models. Search in parameter/hyperparameter space.

🧩 **Feature 2 — ML Algorithm Creation + Mutation.** One level above Feature 1: creates/evolves genuinely new algorithms/equations, not just settings within one. AutoML-Zero / FunSearch / AlphaEvolve-style evolutionary search over program/equation space. Directly operationalizes the "Symbolic Regression / Genetic Programming" taxonomy entry (§5 below) into an actual capability.

🧩 **Feature 3 — Graph/Pathway Evolution Engine (registered 2026-06-20, was the "possible third feature" in §7).** A third, distinct level: operates on the *graph topology itself* — which models/functions connect to which — not a model instance's params (Feature 1) or an algorithm's internals (Feature 2). Consolidates everything found in Blocks 16-18 about this idea:
- **Connection/pathway-reputation memory** (Block 17) — the unit of memory is the edge/pathway, not the model, carrying regime-conditioned outcome stats.
- **Path Discovery Engine** — evaluates whole multi-hop pathways, not single models or edges.
- **Pathway genetics** — crossover two successful pathways into a child, test, keep if better.
- **Pathway death + curiosity-driven pathway creation** — both now formally subsumed by the evaluator's Layer 2 (non-stationary bandit / UCB), not separate hand-built rules (Block 22's finding).
- **Shares the same 5-layer evaluator as Features 1 & 2** (below) — scoring a candidate pathway is the same kind of problem as scoring a candidate model/algorithm, so it reuses Layers 0-4 rather than needing its own.
- **Connects to the Step-10 hierarchy (§7):** with Feature 3 now registered, the three features form a clean stack — Feature 1 fills a function-slot with a model instance, Feature 2 fills it with a newly-created algorithm, Feature 3 decides which slots connect to which. The deeper question of whether slots should be defined at the *function* level (Block 16 Layer-1 categories) rather than the algorithm level is still open, but the three-feature structure itself now matches Step 10's framing.

✅ **Evaluator design — accepted into the plan, ships together with Features 1, 2 & 3 (Blocks 21-22, moved here from §7 2026-06-20).** All three features need this built *before* their mutation engines, or candidates can't be safely scored before replacing an incumbent — that dependency is now a hard gate, not just flagged. Five layers, framework accepted; specific algorithm choices within each layer (e.g. Sliding-Window vs. Discounted UCB) remain implementation details for build time:
- **Layer 0 — data hygiene:** purged + embargoed walk-forward splits (López de Prado 2017) — mandatory; naive k-fold leaks future information via overlapping label windows.
- **Layer 1 — per-candidate significance, regime-aware:** Deflated Sharpe Ratio + Probabilistic Sharpe Ratio/Minimum Track Record Length (Bailey & López de Prado) — catches under-sampled regime-specific scores before they're trusted.
- **Layer 2 — online/non-stationary scoring:** non-stationary multi-armed bandit (Sliding-Window UCB / Discounted UCB) per connection/pathway — subsumes pathway death (low UCB score) and curiosity-driven pathway creation (UCB's built-in exploration bonus) as one mechanism instead of two hand-built rules.
- **Layer 3 — population-level, multi-objective gate:** NSGA-II-style Pareto-front selection across Profit/Sharpe/Drawdown/Stability/Prediction-Quality, paired with PBO/CSCV or Romano-Wolf SPA so the Pareto front itself isn't an overfitting mirage.
- **Layer 4 — anti-gaming anchor:** a small fixed set of known historical regime episodes every promoted candidate must stay sane on.

**Open tension, still not resolved (Rule 16):** regime-conditioning shrinks per-regime sample size, fighting Layer 1's data-sufficiency requirement. Two credible fixes not yet chosen: fewer/broader regime buckets, or hierarchical/partial-pooling Bayesian estimation.

❓ **Implementation order among Features 1, 2 & 3 specifically:** still not set — only their position relative to the *rest of the plan* (dead last, all three together) is decided. Which of the three comes first *between themselves* remains open.

- **24. - **28. Fractal / Multifractal Market Analysis** — Hurst exponent, MFDFA, Fractal Market Hypothesis. Use: scale-invariance/long-range-correlation measurement. Honest caveat: contested in the literature — some studies find it doesn't improve prediction accuracy.

🟡 **Vector Database — five concrete roles identified across the architecture (Block 29, live research + Claude's own synthesis, 2026-06-20), resolving §5's bare "Memory" category placeholder into an actual design:**
1. **Model Genome Database backend** (§5, Block 18 schema) — embed each node's profile (inputs/outputs/regime-affinity/etc.); similarity search pre-filters the 300-1000+ model bank down to K relevant candidates for a given slot before the routing mechanism (GNN/MoE/LLM) chooses among them — a concrete mechanism for Block 18's "don't fully-connect everything" constraint, not just a stated rule.
2. **Pathway-similarity backend for Feature 3's Path Discovery Engine — Claude's own synthesis, not from any pasted source.** Embed pathways (node-sequence + outcome stats); nearest-neighbor search directly implements Block 17 Step 7's "curiosity-driven mutation" (find paths sharing structure, infer a useful slot, experiment with fillers) as a real mechanism instead of a vague heuristic.
3. **RAG ingestion for *unstructured* "online" data** — news, social, on-chain commentary specifically (the unstructured subset of Block 4's raw-data sources). Embed external documents, retrieve top-K relevant ones for whatever model/Connector Intelligence needs context. Explicitly **not** for structured numeric sources (candles, order book) — those go through the Feature Factory, not retrieval.
4. **Persistent Archival Memory tier — adopting Letta/MemGPT's real 3-tier architecture wholesale rather than reinventing it:** Core Memory (current regime/context, always available — maps to the World Model, Block 17 Step 8) + **Archival Memory (the vector DB, long-term semantic search)** + Recall Memory (full history log).
5. **Claude's own added synthesis — regime-similarity via the evaluator's anchor set:** embed the current market window and the evaluator's Layer-4 anchor set of known historical regime episodes (Blocks 21-22) into the same space; nearest-neighbor search gives a continuous regime-similarity score instead of a brittle hand-labeled category, unifying the World Model and the evaluator's anchor set through one mechanism.

**Real implementation options found, none chosen yet:** Pinecone/Milvus (large-scale managed), Qdrant (fast open-source), Weaviate (hybrid + GraphQL), pgvector (if Postgres is already the data platform), Chroma (simplest dev experience). Per Block 3/24's "start small" philosophy already on record, pgvector or Chroma/Qdrant would be the practical starting choice — not a large managed service — until the model bank actually scales toward hundreds of nodes.

**Cross-reference:** real MoE-plus-embeddings research exists (ROUTERRETRIEVER — a router selecting among domain-specific "expert" embedding models per query) — structurally the same problem as §6's MoE-gating Connector Intelligence candidate (Block 7c) choosing among model-bank nodes; worth revisiting when that candidate gets prototyped.

🟡 **How to ADD/USE/CONNECT a node, concretely — live research, Block 35, 2026-06-20.** Block 18/29 said *what* belongs in the model bank and *what metadata* each node needs; this is the *how*, grounded in real, production-proven patterns rather than invented from scratch. Checked against Rule 23 first: all of the below operate purely on a generic interface and know nothing about stocks/candles, so they're consistent with §0.
- **Adding a node — common interface, not a custom one per model:** scikit-learn's `fit`/`predict`/`transform` Estimator API is the most proven real precedent for "every model, regardless of internals, exposes the same small set of methods" — adopt that convention rather than inventing a new one. For node types that don't naturally fit that shape (HMMs, Kalman filters, a symbolic-regression equation), **MLflow's `pyfunc` flavor** is the more general fallback: wrap *anything* behind a single `predict()` method, framework-agnostic, self-contained with its own dependencies.
- **Using a node:** once wrapped behind that common interface, calling any node looks identical regardless of what's inside it — this is the literal mechanical realization of §0's "data bends to the system" principle, demonstrated in production by **Ray Serve's deployment-graph model composition**, where calls to wildly different models (different frameworks, different resource needs — GPU vs. CPU) "look just like function calls" through a `DeploymentHandle`.
- **Connecting nodes into a graph — two real, complementary mechanisms, not one we'd have to invent:** (a) **Ray Serve's deployment graphs** — bind models together by passing them into each other's constructors; each node scales/configures independently; (b) **LangChain's LCEL `Runnable` interface** — any two components implementing `.invoke()` compose via the `|` pipe operator, with `RunnableSequence` for chains and `RunnableParallel` for fan-out (e.g. feeding one input to several pattern-discovery nodes at once before merging) — a clean, pythonic candidate for how Connector Intelligence v0 (build-order step 2) actually executes a wired pathway.
- **Registering/discovering the whole bank, not just one path:** **Kedro's node + Data Catalog + Pipeline trio** is the closest real match to the still-conceptual Model Genome Database (§5, Block 18) — a catalog of named, typed artifacts (here: models) decoupled from pipeline logic, with **Kedro-Viz** giving free DAG visualization of the resulting graph as a side benefit.
- **Honest scope limit on ONNX:** strong, mature option for cross-framework/hardware portability, but primarily suited to neural-network-shaped models; classical/non-neural nodes (HMM, ARIMA, a discovered equation) have partial or awkward ONNX support. Treat as a later-stage optimization for the neural subset of the bank, not a starting requirement for every node.
🟡 **From Block 16 (pasted ChatGPT content, Part 1) — a complementary 5-layer framing**, focused on model-graph evolution rather than data translation: (1) Primitive Intelligence Units — the model bank, grouped by function (Pattern/Sequence/Probability/Noise/Equation/Optimization units) rather than by technical mechanism; (2) Connector Intelligence — builds a dynamic graph where nodes=models and a router decides which edges (model-to-model feeds) exist; (3) Architecture Search — explores many candidate graphs (which model feeds which), scored on profit/accuracy/stability/Sharpe/drawdown; (4) Evolution Engine — treats whole graph-architectures like DNA: crossover two architectures, mutate, evaluate, keep winners; (5) Memory — stores which architecture patterns worked under which market regime (bull/high-vol/sideways) and biases future architecture search accordingly. Complements, doesn't contradict, the Block 4 data-translation pipeline — that one is about getting data *into* models, this one is about evolving the *graph of models themselves*.
🟡 **"Models as electronic components" analogy** (Block 16, echoed again in Block 19's duplicate paste) — models as transistors/logic-gates that combine into a "computer," alongside the existing compiler/internet-protocol analogies (Blocks 4-5). The two framings connect: a shared belief format is "the voltage/signal standard" that lets components plug into each other at all, the same role TCP/IP plays for the internet analogy.
🟡 **Independent corroboration (Block 16):** a second, independent source (the owner's prior ChatGPT conversation) reached the same conclusion Claude reached in Block 7 — the hard, novel research problem is the connector intelligence itself (deciding which models connect to which, when to disconnect, when to create new pathways), not the size of the model catalog. 🟡 **Core principle from Block 17 (pasted ChatGPT content, Part 2) — score CONNECTIONS, not models.** The memory unit shifts: model → connection (edge) → full pathway (multi-hop chain), each carrying usage count + regime-conditioned outcome stats (e.g. bull/bear/volatile performance) + a confidence/reputation score. "The graph itself becomes the memory, not the models" — synapse-like, not symbol-like. This sharpens (doesn't replace) the Block 16 Layer-5 memory idea: memory attaches to *edges and paths*, specifically.

🟡 **Third Connector Intelligence routing-mechanism candidate (Block 17):** a Graph Neural Network that ingests node performance + connection performance + current market regime + recent success/failure, and predicts which connection to activate next — added alongside the existing two candidates (MoE-gating, LLM-tool-calling) from Block 7c/7d.

🟡 **World Model component (Block 17):** the connector must condition routing on the current market regime (Bull/Bear/Range/High-Vol/Low-Vol/News-Shock/Liquidity-Crisis) — the same pathway is not always best across regimes. Sharpens Block 16 Layer-5 into an explicit required component, distinct from the GNN mechanism itself (the World Model is the *context input*; the GNN is the *mechanism* that consumes it).

🟡 **Concrete pruning + mutation rules proposed (Block 17), illustrative not validated:** (a) pathway/connection death — remove a connection if its marginal improvement over its last ~5,000 uses falls below a small threshold (source's example: 0.001%), synaptic-pruning-style; (b) structured ("curiosity-driven") mutation — instead of pure-random mutation, find shared sub-structure across two independently-successful pathways (e.g. both route `Wavelet → ??? → Transformer`) and target new candidates specifically at the differing slot, rather than mutating blindly.

🟡 **Concrete 8-layer ordering proposed (Block 18, Part 3)**, refining Block 16 Layer-1's 6 function categories into an explicit sequence: Signal → Noise → Pattern → Sequence → Probability → Equation → Decision → RL. Worked example pathways given: `Wavelet→HDBSCAN→HMM→PatchTST→Kalman→PySR→PPO` and `SSA→GMM→Transformer→Bayesian Network→SAC`. Paired with an explicit constraint: don't fully-connect 300-1000+ models directly — let the Connector Intelligence search *within and across adjacent layers*, not over an unconstrained complete graph.

🟡 **"Model Genome Database" schema proposed (Block 18)** — the source's candidate answer to "what does each node need to carry": Model ID, Inputs, Outputs, Latency, Memory Cost, Training Cost, Confidence, Best Market Regime, Compatible Models, Historical Success. This operationalizes Block 17's connection/pathway-reputation memory into a concrete per-node metadata schema. Source's own conclusion, now corroborated three times over (Blocks 7, 16, 17, 18 independently converge on it): the research problem is this database + the search/evolution over it, not collecting more models — "that part is easy."
